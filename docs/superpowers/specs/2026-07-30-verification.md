# DockMinimizer 검증 기록

검증일: 2026-08-03
빌드: `feat/dock-minimizer`, `/Applications/DockMinimizer.app` (self-signed `DockMinimizer Self Signed`)
환경: macOS 26.5.2 (Tahoe), arm64, 단일 디스플레이 1800×1169

검증은 대부분 자동화했다. HID 레벨(`.cghidEventTap`)로 클릭을 합성하고 대상 앱의 윈도우 최소화 상태를 AX로 직접 읽는다. 사람이 눈으로 관찰하는 방식보다 재현 가능하고, 실제로 이 방식 덕분에 Phase 0에서 잘못 내린 결론(Plan A)을 구현 단계에서 잡을 수 있었다.

도구는 저장소에 있다. 코드를 고친 뒤 다시 돌릴 것.

```bash
swift run DockProbe verify   # 설치된 앱의 동작 검증 (11개 항목)
swift run DockProbe ui       # 메뉴바·설정 창·로그인 항목 (15개 항목)
swift run DockProbe race     # 리슨 전용 탭 회귀 테스트 — 앱을 끄고 실행할 것
```

`race`는 이 프로젝트에서 가장 미묘한 버그의 회귀 테스트다. 대조군(클릭 없이 최소화)은
유지되고 실험군(Dock 클릭과 동시 최소화)은 되돌려져야 한다. 실험군이 유지되면 macOS
동작이 바뀐 것이므로 리슨 전용 탭으로 되돌릴 수 있는지 재검토한다.

## 핵심 동작

| 항목 | 결과 | 근거 |
|---|---|---|
| 최소화 → 복원 → 최소화 → 복원 토글 | PASS | 4회 연속 클릭이 매번 번갈아 동작 |
| **빠른 연속 클릭 (정착 구간)** | PASS | 50ms / 150ms / 300ms 간격 모두 최소화 → 복원 |
| 프론트모스트가 아닌 앱 클릭 → 평소대로 활성화 | PASS | Safari 활성화, 메모는 최소화되지 않음 |
| 최소화 직후 이웃 아이콘 클릭 | PASS | Safari 아이콘이 22.5pt 이동했음에도 올바른 앱 활성화 |
| 단위 테스트 | PASS | 24/24 |
| 클린 빌드 후 접근성 권한 유지 | PASS | `.build`/`build` 삭제 후 재설치해도 탭 정상 시작 |

Dock 재정렬은 실측으로 확인했다. 메모를 최소화하자 Safari 아이콘의 x좌표가 **22.5pt**(아이콘 폭 45pt의 정확히 절반) 이동했다. `DockIndex.refreshAfterWindowChange()`가 이를 흡수한다.

## 입력 변형

| 항목 | 결과 | 근거 |
|---|---|---|
| 수정자 없는 클릭 | 최소화됨 | 기준선 |
| ⌘클릭 | 개입 안 함 | `ClickRouter`의 수정자 가드 |
| 옵션클릭 | 개입 안 함 | 동일 |
| 더블클릭 (50ms) | 이상 상태 없음 | 정착 구간이 두 번째 클릭을 올바르게 복원으로 처리 |
| 우클릭 | 개입 불가 | 이벤트 마스크가 leftMouseDown/Up 뿐이라 구조적으로 도달하지 않는다 |
| 프론트모스트 앱 아이콘 드래그 | **동작하지 않음 (알려진 제약)** | 아래 참조 |

**드래그 제약:** 프론트모스트 앱 아이콘의 mouseDown을 삼키므로 Dock이 드래그를 시작하지 못한다. 통과시키면 Dock이 우리 최소화를 되돌리므로 양립할 수 없다. 다른 아이콘의 드래그는 영향받지 않는다.

## UI (2026-08-04 추가)

메뉴와 설정 창을 접근성 API로 직접 읽고 눌러 검증했다. `swift run DockProbe ui`로 재현한다.

| 항목 | 결과 | 근거 |
|---|---|---|
| 메뉴바 항목 구성 | PASS | `접근성 권한: 정상`(비활성 레이블), `✓ 활성화`, `✓ 로그인 시 시작`, `설정...`, `종료` |
| `재실행` 항목 숨김 | PASS | 권한과 탭이 모두 정상일 때 숨겨진다 (의도된 동작) |
| 설정 창 렌더링 | PASS | 활성화 체크박스, `권한이 부여되었습니다`, 제외 목록, `추가...`/`제거` |
| 선택 없을 때 `제거` 비활성 | PASS | `AXEnabled = false` |
| **메뉴바 ↔ 설정 창 동기화** | PASS | 창을 열어 둔 채 메뉴바에서 토글 → 창을 다시 열면 반영됨. 원복 후에도 일치 |
| 로그인 시 시작 토글 | PASS | 켜짐 → 꺼짐 → 켜짐 양방향 확인. 검사 전 상태로 복원함 |

`SMAppService` 상태는 메뉴 항목의 체크마크로 확인했다. `sfltool dumpbtm`은 토글 직후 응답이 멈추는 일이 있어 신뢰할 수 있는 판정 수단이 아니다.

## 남은 항목 — 사람이 확인해야 함

자동화하지 못했거나 이 환경에서 재현할 수 없는 것들이다.

- [ ] **멀티 디스플레이** — 단일 디스플레이 환경이라 측정 불가. Dock이 있는 화면과 없는 화면 양쪽에서 확인 필요
- [ ] **여러 스페이스에 걸친 윈도우**
- [ ] **제외 앱 추가 UI** — `NSOpenPanel`은 모달이라 자동화하지 않았다. 제외 목록 자체는 `UserDefaults`로 검증했다
- [ ] **장시간 실행 (수 시간)** — 이벤트 탭이 죽지 않는지. `log show ... | grep -E '느립니다|비활성화'`가 비어 있어야 한다
- [ ] **권한 회수/재부여의 즉시 반영** — 실측에서 권한 **부여**는 실행 중인 프로세스에 반영되지 않았고 재시작이 필요했다. 회수 방향은 측정하지 못했다. 앱은 두 경우 모두를 처리한다: 권한은 있는데 탭이 없으면 메뉴바가 `권한 부여됨 — 재실행해야 적용됩니다`를 표시하고 `재실행` 항목을 보여 준다
- [ ] **기능을 끈 뒤 전부 최소화된 앱의 복구 경로** — Dock의 최소화 윈도우 항목으로 복구 가능한지

## 미해결 — 재현되지 않은 1회성 실패

2026-08-04, GPL 라이선스 적용 직후 `DockProbe verify`가 **6 PASS / 5 FAIL**로 한 번 실패했다. 실패한 5개는 "앱이 동작해야 통과"하는 항목 전부였고, 통과한 6개는 "앱이 개입하지 않아야 통과"하는 항목이었다. 즉 **그 시점에 앱이 아무 동작도 하지 않았다.** 앱 로그에는 `Coordinator 시작`과 `이벤트 탭 시작`이 정상으로 남아 있었다.

이후 같은 조건에서 **7회 이상 연속 11/11 통과**했고, 다음 가설을 각각 검증해 모두 배제했다.

| 가설 | 검증 방법 | 결과 |
|---|---|---|
| 앱 시작 직후 캐시가 비어 있는 구간 | 실행 후 0.5 / 1 / 2 / 4초 시점에 클릭 | 전부 정상. 0.5초면 준비됨 |
| 번들 교체 직후 TCC 재평가 구간 | `install.sh` 직후 1 / 3 / 6초 시점에 클릭 | 전부 정상 |
| 시작 직후 CPU 부하로 초기 AX 조회 지연 | 앱 실행과 동시에 릴리스 빌드를 걸고 0.6초 시점에 클릭 | 전부 정상 |

### 두 번째 사례 (2026-08-04)

`DockProbe ui`를 돌린 직후 `verify`가 **10 PASS / 1 FAIL**로 한 번 실패했다. 첫 번째 사례와 달리 하나만 실패했으므로 "앱이 아무 동작도 안 함"은 아니다. **어느 항목이 실패했는지 포착하지 못했다** — 출력의 마지막 두 줄만 보고 있었다. 직후 4회 연속 11/11 통과했다.

`ui`가 직전에 활성화 토글과 로그인 항목을 껐다 켜므로 그 여파일 가능성이 있으나 확인하지 못했다. 실무적으로는 **`verify`를 `ui` 직후에 이어 돌리지 말고 따로 돌리는 편이 낫다.**

실패를 다시 만나면 반드시 전체 출력을 남길 것:

```bash
swift run DockProbe verify 2>&1 | tee /tmp/verify.log
```

**원인 미상.** 앱이 조용히 무동작 상태가 되는 경로가 하나 더 있을 수 있으므로 기록해 둔다. 재발하면 다음을 확인할 것:

- `log show --predicate 'process == "DockMinimizer"' | grep -E '느립니다|비활성화'` — 이벤트 탭이 타임아웃으로 죽었는지
- `DockIndex.snapshot`이 비어 있었는지 (`Coordinator`의 decide 클로저에 임시 진단 로그를 넣어 `icons=` 값을 확인)
- Dock 확대 설정이 켜져 있었는지 (켜져 있으면 의도적으로 빈 스냅샷을 낸다)

## 검증 중 발견해 고친 결함

1. **Plan A(리슨 전용 탭)가 틀렸다.** Phase 0에서 "Dock은 아무 것도 하지 않는다"고 결론냈으나, 그것은 되돌릴 대상이 없을 때의 관찰이었다. 우리가 최소화하면 Dock이 같은 클릭을 처리하며 100ms 안에 원상복구한다. `AXUIElementSetAttributeValue`가 `.success`를 반환하고 로그도 정상이라 증상은 "아무 일도 일어나지 않음"으로만 보였다. 액티브 탭 + 클릭 삼킴으로 수정.

2. **삼킴 플래그에 유효 기간이 없었다.** 짝이 되는 mouseUp이 끝내 오지 않으면 플래그가 남아 한참 뒤의 무관한 클릭을 삼킨다. 1초 유효 기간을 부여.

3. **빠른 연속 클릭이 검증되지 않고 있었다.** 초기 검증 도구가 클릭 사이에 1.6초를 기다려, 800ms 정착 구간을 한 번도 건드리지 않았다. 캐시가 타이머로 이미 갱신된 뒤에 다음 클릭이 도착했기 때문이다. 50/150/300ms 간격을 추가해 실제로 검증했고, 전부 통과했다.

4. **측정 도구 자체의 함정.** `CGEvent.post(tap: .cgSessionEventTap)`로 보낸 합성 클릭은 Dock에 전달되지 않는다. `.cghidEventTap`으로 보내야 한다. 이것을 모르고 측정하면 모든 결과가 "아무 일도 일어나지 않음"으로 나와 잘못된 결론에 이른다.
